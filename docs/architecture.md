# 出席管理システム刷新方針

検討日: 2026-10-28。設計提案であり、本番変更は行っていない。技術選定理由、一般的な構成、Codex操作性、過剰設計回避を重視する追加条件を反映。多少の色・大きさの変更は許容。

## 決定案

- 配信: 生徒・先生の画面とAPIを1つのCloudflare Workersアプリへまとめ、Workers Static Assetsで静的ファイルを配信する。DBは同アプリからD1へ接続する。
- 既存リンク: Firebase Hosting Sparkを転送専用に残す。既存の `.html` URLから対応する新画面へ302転送し、配布済みQRを維持する。転送後のアドレスバーは変わる。
- UI互換: ログイン方法、表示内容の意味、主要な画面遷移と操作手順を維持する。色・サイズ等の小さな見た目変更は許容。DOM/CSSの一致自体は要求しない。
- フロントエンド: React + TypeScript + Vite。状態と表示を分離して再実装し、既存の主要操作に対応するコンポーネントを構成。ページ単位でコード分割し、ログイン画面に先生用編集機能を読み込ませない。
- API: Cloudflare Workers Free + Hono + Zod。
- DB: Cloudflare D1 Free。SQLマイグレーションをGit管理し、ブラウザからのDB直接アクセスを廃止。
- アプリの単位: 1リポジトリ・1アプリ・1本番DB。生徒・先生・公開APIはルートと権限で分け、別サービスにはしない。
- 認証: 生徒は苗字 + 共通パスワード をサーバーで検証。先生は生徒用とは別の覚えやすい合言葉を日本時間で1日1回、当日最初に入力。
- 公式サイト: 公開用休講日APIを参照する。管理情報を公開APIに含めない。
- 検証: Vitestで日付・権限・業務ルール、Playwrightで操作と画面差分。
- 運用: 無料プランのみ。課金プランへの自動移行に依存しない。無料枠超過時の停止はあり得る。

ユーザーが当初から許容した「Firebase Hostingを転送専用にする」案を採用し、前案の生徒だけFirebase配信とする構成を改める。ドメインが変わるため、保存済みパスワードの自動入力や古いセッションはそのまま移らない場合がある。苗字・パスワードの入力内容やログイン手順は維持し、実機でこの差を確認する。アドレスバーや自動入力までの完全な互換性が必要になれば、生徒の静的配信だけ旧Hostingに残す案へ戻す。その場合は別サイト認証の複雑さを受け入れる必要がある。

## 技術選定の判断記録

### 選定基準

必須条件は無料運用・既存の認証操作・既存リンク・業務機能の維持。そのうえで、(1)選定理由を具体的に説明できる、(2)一般的で引継ぎやすい構成、(3)Codexからプラグイン/MCPとCLIで操作・検証できる、(4)規模に対して過剰でない、を比較基準にする。現在未導入のプラグインも導入可能なら候補とし、現在の接続状態で技術選定を固定しない。

採用技術の唯一性は主張しない。成立する複数の選択肢から、利益と負担を比較して選ぶ。TypeScriptやReactの導入そのものによる安全性・速度向上は約束しない。

### React + TypeScript + Vite

現在は取得済みの予定、保存前の変更、元の登録者、残席、モーダル、表示期間などを複数の可変オブジェクトとDOM操作で同期させている。予定表の描画処理も画面間で重複している。この状態と表示の対応をコンポーネントと型で明示するためにReactを採用する。

- サーバーから取得した予定と、保存前の取消選択を別の状態として扱う。
- セルの色、丸印、残席表示を状態から導出し、クリックのたびにHTMLとクラスを手作業で同期しない。
- 通常/B/Cの選択、休講判定、編集権限はUIから切り離して共通化。Reactコンポーネントは判定結果を描画する。
- TypeScriptで日付、コマ、生徒ID、権限、API応答を区別する。ただしHTTP境界はZod等で実行時検証する。
- Viteを使って静的ファイルを生成する。既存 `.html` パスをエントリまたはHosting設定で維持する。

VueやSvelteでもこの設計は成立する。Reactを選ぶ差は開発者の習熟・引継ぎ・利用する検証ツールとの相性であり、Reactだけが可能という説明はしない。担当者が他のフレームワークに十分習熟している場合は再評価可能。

Next.jsも静的出力ができるため「Firebaseに置けない」は不採用理由にならない。ただし今回はログイン後の操作が中心で、検索流入・SSR・Server Componentsを必要条件としていない。APIを独立させたまま静的配信するなら、追加するサーバー機能に見合う利益が現状では小さいためViteを選ぶ。

Reactの負担は実行時JSの増加と書き直しコスト。軽いログイン画面にもアプリ全体を読み込ませず、コード分割と実機計測で管理する。利用人数が少ないことと、UI状態の複雑さは別の判断軸。

### Workers + Hono + Zod

生徒による追加登録禁止、先生権限、非公開月の参照拒否は、画面のボタンを隠すだけでは成立しない。ブラウザの申告を信用しないAPI層が必要になる。Workersは常駐サーバーの管理を避け、無料枠内でAPIを稼働させるための選択。

HonoはHTTPルーティング、認証・認可ミドルウェア、エラー応答をまとめるために使う。Web標準APIを基盤としWorkersへ適合する。標準fetchだけでも実装できるが、APIが増えた際の認証チェックや入力検証の抜けを減らす構造を優先する。Hono自体が認可の正しさを保証するわけではない。

Node.js + Express等も成立するが、今回は常駐環境の用意やWorkers向けの互換対応を増やす利点がない。WorkersのCPU・実行環境制約とCloudflare依存を受け入れる代わりに運用負担を減らす。

### D1 / SQLite + SQLマイグレーション

中心となるデータは「生徒×日付×コマの予約」と、科目・休講・月別公開の関連である。重複禁止、一括生成、日別人数集計、改名時の参照維持をDBの制約とSQLで表すため、リレーショナルDBを採用する。

Firestoreでも認証・Rules・トランザクション・読取用モデルを適切に設計すれば改善できる。日付のずれはFirestoreの欠陥ではなくアプリの実装の問題。移行不要というFirestore維持の利点もある。そのうえで今回はデータ構造も改め、集計用データの手動同期を減らす方を優先する。

D1をPostgreSQLより優先する理由は、現状の小規模な更新頻度と単一塾の用途で、無料枠・Workersとの接続・運用負担の条件に合うため。SQLの一般性だけが目的ならPostgreSQLも有力であり、高い同時書込みやPostgreSQL固有機能が必要になれば再検討する。

D1は汎用PostgreSQLと同じではない。バッチAPIや条件付きSQLの単位で整合性を設計し、通常のアプリ内トランザクションと同じ書き方が自由にできる前提を置かない。月生成や移行は書込枠・実行時間も検証する。

初期案ではORMを必須にしない。SQL、スキーマ変更、索引、集計を明示し、HTTP層からデータアクセスを分離する。DrizzleはD1対応の候補だが、型付けやスキーマ管理の重複が実装上の負担になった場合に導入を判断する。ライブラリ数を増やすことを成果にしない。

### 配信先を集約しFirebase Hostingを転送専用にする理由

転送はユーザーが許容している。先生・生徒の画面とAPIを同一オリジンへまとめ、Cookie認証を共通化する。CORSや別サイトCookie、ブラウザ内Bearer保管と先生専用の認証方式という分岐を減らす。

Firebase Hostingの役割は配布済みQR・ブックマークの入口を維持することだけ。アプリ本体は公式のReact + Vite + Workers構成を土台にする。旧URLごとの対応表を作り、ログイン以外の直リンクも引き継ぐ。

代償は転送先のURLが見えることと、サイト別のパスワード自動入力・保存状態が移らない場合があること。全く無変更の体験とは説明しない。アドレスバー不変を必須にする場合の代替案も残す。

### 構成候補の比較

| 候補 | 利点 | 今回の判断 |
| --- | --- | --- |
| React + Firebase Auth + Firestore + Hosting | 小規模アプリの一般的な選択肢。公式プラグイン/MCPあり。既存基盤を活用できる | 有力な代替。既存の苗字・4文字パスワードとの対応づけ、取消と人数集計の整合性をAuth/Rules/トランザクションで設計する必要がある。今回は小さなAPIで権限を集中管理しSQL集計を使う設計を優先。Firebaseが危険・遅いことを理由にしない |
| React + 小さなAPI + Supabase/PostgreSQL | 一般的なRDB。SQL・マイグレーション・ログ・型生成のプラグイン操作が揃う | 有力な代替。ただしFreeは1週間非稼働で休止、アクティブ2プロジェクトまで。休塾期間と開発/本番環境を考慮する必要があり、無料の継続運用条件では優先しない |
| Next.js + PostgreSQL | 一般的なフルスタック構成。SSR等が必要なら有力 | 今回はSSR要件なし。ホストとDBの無料条件を別途満たす必要がある。Vercel Hobbyは塾実運用の基盤にしない |

### Codex駆動開発のために用意するもの

- Cloudflareプラグイン: ツール仕様でD1作成・SQL実行・インポート/エクスポート、Workerバージョン・デプロイ、Secret設定のAPIを確認。接続の認証確認にも成功。各アカウントの操作権限やデプロイ全工程の成功は実装時に検証する。
- Firebaseプラグイン: 公式プラグインを検索した後、このセッションでツールが利用可能になり、環境取得にも成功。Firebaseユーザーは未認証、アクティブプロジェクト未選択、firebase.jsonなし。本番DBへのアクセス成功までは未確認。旧DB調査・移行・Rules確認とHosting転送に利用する。提供ツールで足りない抽出やデプロイは公式CLI/SDKで補う。
- GitHubプラグイン: 変更確認、PR、CIの確認に利用する。開発コマンド自体はリポジトリ内へ保存する。
- ブラウザ操作: ローカル/検証環境で画面遷移、ログイン、取消、先生編集、QR由来URLを検証する。
- ローカルD1: 架空データで再現可能な環境を作る。remote=trueや本番接続をローカル検証の既定にしない。
- 単一コマンドの検証: 型検査、業務ルール/日付/権限/DBのテスト、ビルド、E2Eを決まったコマンドで実行できるようにする。
- SQLマイグレーション、設定、テストデータをGit管理。MCPで試した変更だけを本番に残さない。
- 最初の認証や本番移行時の意図確認を除き、人がコンソールを操作しないと前へ進めない手順を減らす。プラグインがあるだけで完全自動化できるとは説明しない。

### 追加しない技術・構造

マイクロサービス、独立した生徒/先生バックエンド、Redis、キュー、GraphQL、WebSocket、Kubernetes、独自の汎用認証基盤、汎用マルチテナント機構は初期構成に入れない。状態管理の外部ライブラリ、ORM、複雑なモノレポ管理ツールも必要性が確認できるまで追加しない。APIで独自ログインの互換性を受け持つが、Cookie・乱数・パスワード検証等の暗号要素を独自発明しない。

### 設計を評価する指標

- 正しさ: 日付×コマ×生徒集合の移行照合、不正な追加・他人更新・非公開月参照の拒否。
- 競合耐性: 同時取消、リクエスト再送、月生成失敗によって予約と人数が矛盾しないこと。
- 体験の互換性: 既存QR、苗字と共通パスワード、主要操作の順番と意味を維持。
- 性能: 初回表示、月切替、保存完了のp50/p95、通信回数、JS転送量を旧版と比較。
- 無料運用: 通常日と月生成日にCPU時間・rows_read・rows_written・転送量が無料枠に収まること。
- 復旧: 1時間枠の移行リハーサルと、書込再開後の変更を失わない復旧試験。

## セキュリティ境界

### 生徒

1. 既存と同じ入力欄、同じ入力内容でログインする。空白処理やエラー文言も実行コードと合わせる。
2. APIが認証し、内部student_idに結びつく推測困難な失効可能セッションを発行する。
3. 画面とAPIを同一オリジンへ置き、Secure / HttpOnly / SameSiteのCookieを利用する。生徒セッションは先生の当日中の保持と分け、現行のログインの手間に近づける。同じ端末での生徒切替や複数タブも互換検証に含める。
4. APIはURLやリクエスト本文の名前を権限の根拠にしない。本人の予定、必要な集計値、公開済み情報だけ返す。全生徒名簿は返さない。
5. 生徒向け更新APIは取消専用。新規追加、他人の予定、当日・過去、非公開月、対象外コマへの変更を拒否する。実際の保存時点の日本時間で判断。
6. キャンセル取り消しは保存前のローカル編集だけ。保存済み取消の復活は先生の操作に限定する。

苗字と共通パスワードでは、他人の苗字とパスワードを知る人のなりすましは防げない。同姓の識別問題も自動的には解決しない。ユーザー要件として維持し、強い本人確認とは説明しない。

セッションの秘密をJavaScriptから読み取れる保管先に置かない。Cookie認証の更新操作にはCSRF対策を適用する。HttpOnlyでもXSSの被害は防ぎきれないため、文字列をHTML挿入しない、外部スクリプトを絞る、CSPを適用する。公開用休講日APIだけ必要な範囲でCORSを設定する。

### 先生

- 完全な無認証では第三者との区別ができないため、許容された日本時間で1日1回、当日最初のパスワード方式を採用。
- 先生用の合言葉は生徒の共通パスワードと分離し、公開リポジトリには入れない。
- 先生画面とAPIを同一オリジンにし、Secure / HttpOnly / SameSiteのCookieを利用。サーバー側でも有効期限・失効を管理。
- Cookie認証の更新操作にはCSRF対策を実施。端末の紛失時はセッション失効。
- URLを知っていることだけでは先生権限を与えない。

全APIに入力検証、SQLプレースホルダ、認証と権限判定を実装。ログインはレート制限を行い、生徒を長期ロックする運用は避ける。合言葉の検証方式はWorkers FreeのCPU上限を含めて試作検証する。セッションやパスワードをログ出力しない。

## データ設計

```text
students             不変ID、表示名、現在のログイン名、読み、在籍状態
schedule_patterns    通常・臨時B・臨時C
pattern_slots        パターン×曜日×コマの科目と定員
calendar_days        実日付、休講状態、その日のパターン
monthly_templates    月×生徒×曜日×コマ
month_publications   月単位の公開状態
reservations         生徒ID×実日付×コマ
announcements        お知らせ
login_events         現行の閲覧者確認に必要なログイン記録
audit_events         先生・生徒による変更履歴、旧値と新値
sessions             生徒・先生の失効可能セッション
migration_mapping    元パスと実日付の対応、変換規則、元データハッシュ
```

- 授業日は検証済み `YYYY-MM-DD` の日付文字列で保存する。表示日が11月1日ならDBも11月1日。
- 更新時刻・ログイン時刻はUTCのタイムスタンプ。業務上の「今日」はAsia/Tokyoで算出。
- 授業日の処理にローカル0時のDateをtoISOStringで変換する方法を使わない。ブラウザのタイムゾーンから独立させる。
- 生徒名を主キーにしない。改名で過去データのコピー・移動が発生しない設計。
- reservationsには生徒ID・日付・コマの一意制約、必要な外部キー・CHECK制約と索引を設定。
- 人数は予約からSQL集計。古いattendanceCountを正として移植せず、比較検証の材料にする。二重管理と競合上書きを廃止。
- 取消は条件付きの原子的更新・削除と監査記録。再送で二重減算しない。
- 月次生成は作業版を生成・検証してから短い原子的切替で公開する。失敗途中の空の月を見せない。ジョブ再実行は冪等にする。
- 当月以降のテンプレートを再生成した際の手動変更の扱いは、現行の実行コードに基づく互換テストで固定する。

## 速度方針

- 画面描画のために生徒数×日数でDB要求を増やさない。
- 月別画面は本人予定、科目、休講、残席、公開状態を集約APIで返す。先生画面も表示範囲を一括取得。
- 既存の取得最適化は一部入っているが、画面ごとの再取得や重複した処理を共通化する。
- FirebaseブラウザSDKの読込・初期化を新画面から除く。
- CSSと骨格を先に表示し、必要なJSだけ読み込む。予定一覧は生徒が初回14日、先生が初回3日、以降は双方14日ずつ追加。表示する日付だけをAPIで取得し、取得済み範囲を画面内で再利用する。
- 保存後は対象データを最新化。フォーカス復帰時にも再検証。短周期の常時ポーリングは採用しない。
- 個人データは共有CDNキャッシュに入れない。静的アセットだけ長期キャッシュ。HTMLは更新を検知できる配信設定。
- 本番相当端末・通信で旧新を比較。初回表示、月切替、保存完了のp50/p95を測定し、性能向上は実測値で説明する。

## 日付修正と移行

現在は例えば月次生成でローカル0時をtoISOStringにし、先生画面では明示的な前日補正も使っている。月の親パスと子の日付の月が一致しないこともある。ログイン記録は時刻の影響も受ける。全コレクション一律の+1日は行わない。

1. 初回は権限を持つローカルスクリプトでFirestoreを読み取り、JSON/JSONLへ抽出。CSVは目視確認用。Adminの資格情報はGitに入れない。
2. 元データは変更せず保全し、各保存処理と読取処理からコレクション・フィールドごとの日付変換表を作る。
3. 過去3か月と当月、登録済みの将来予定・将来テンプレートを移す。3か月の正確な開始日を移行設定へ記録。名簿、科目3種類、公開設定、休講日、お知らせ等の現役マスタは履歴期間に関係なく移す。
4. 月初・月末・年末年始・閏日、0時と9時前後を確認。元パスの月と変換後の月の不一致、重複・矛盾を自動検出。
5. 旧画面で先生が意図している表示日と新画面の実日付を照合。旧画面間でも表示が違う場合は代表レコードを運用者に確認し、推測で上書きしない。
6. 対応表・件数・日付×コマ×生徒集合・残席・休講・適用パターン・公開状態の比較レポートを生成。問題が未解決ならリリースしない。
7. 開発中の差分は正規化データのキーと内容ハッシュを比較して検出。updatedAtがなくても、追加・変更・削除すべて反映できるようにする。
8. メンテ中の最終取込は対象範囲を再抽出して照合。小規模なので最終全量置換も選択肢。削除済み予定を残す単純upsertは禁止。

本番データ未取得のため、実際の日付変換規則と所要時間は現時点で未確定。事前リハーサルをリリース条件にする。

## 約1時間の切替手順

| 目安 | 操作 |
| --- | --- |
| 0–10分 | メンテ画面化。旧Firestoreへの一般利用者の書込みをRulesで停止。開いたままの旧タブも保存不能にし、移行用管理アクセスは維持 |
| 10–25分 | 最終抽出、初回移行との差分確認、削除を含め新DB更新 |
| 25–40分 | 日付・コマ・生徒集合の機械照合、月初月末と3種類の授業パターンを確認 |
| 40–50分 | 新アプリの配信を確認し、旧URLからの転送を有効化。ログイン・取消・先生編集・CSVを検証 |
| 50–60分 | 不一致がなければ開放。不一致があれば書込み開放前に旧システムへ戻す |

1時間以内は約束値ではなく、同規模データのリハーサル実績で判断する。実習用環境でのチェックはダミーデータを用い、本番での検証操作は事前に対象と復旧方法を定める。

旧Firestoreの書込みを止める作業は不可欠。Hostingを変更するだけでは古いタブからの書込みが残る。Firebase側は旧リンクの転送を残し、旧管理HTMLが新たに実行されない配信設定にする。

切替前の旧セッションはサーバー認証の証明ではないため、studentNameだけで新セッションを発行しない。切替をまたぐ古いタブは更新時に既存と同じログイン画面へ戻る可能性がある。初回だけを含め完全に無操作の切替は保証しない。

## 復旧

- ソース・配信物・旧Rules・旧DB抽出・変換対応表を保存する。
- 書込み再開前なら旧Hostingと旧Rulesへ戻せる。
- 書込み再開後は新DBでの取消・追加を無視して旧DBへ戻さない。新旧差分を逆移行できることをリハーサルで検証するか、メンテ中に新システムを修正して復旧する。
- 新DBの実日付と旧Firestoreの日付・月パスを逆変換する対応を保持する。
- D1 FreeのTime Travelは7日。別途、暗号化したSQLエクスポートを非公開の保管先に保存し、復元手順も試す。DBバックアップを公開GitHubへ置かない。
- 旧DBの削除や長期データの自動削除は今回の移行対象から分離する。

## 休講日の公式サイト連携

`GET /public/v1/closures?from=YYYY-MM-DD&to=YYYY-MM-DD` を公開する。範囲に上限を設け、公開可能な日付・必要なら公開用理由・更新時刻・スキーマ版のみ返す。

先生が休講を更新すると同じcalendar_daysを公式が読む。別DBへの転記は不要。ETagと短いキャッシュを使い、更新反映の目安は5分以内。公式側がサーバーから取得する場合もブラウザから取得する場合も扱える形式にする。障害時は最終正常取得分と更新時刻を表示し、空の配列を返して「休講なし」と誤認させない。

公開用休講日と生徒向け月公開は別の概念として扱う。先生画面に公開操作を増やすことは今回の互換要件と衝突するため、初期方針は「設定した休講日は公式掲載可能」とし、現行データの適性を確認する。

## 無料枠と採用理由

公式ドキュメント確認時点:

| サービス | 無料枠と留意点 |
| --- | --- |
| Firebase Hosting Spark | 保存10GB、転送10GB/月。超過時は配信停止等の制限があり、無制限無料ではない |
| Cloudflare Workers Free | 10万リクエスト/日、CPU 10ms/呼出。ネットワーク待ち時間とCPU時間は別。複雑な生成処理は事前試作・分割が必要 |
| Cloudflare D1 Free | 読取500万行/日、書込10万行/日。1DB 500MB、アカウント計5GB。索引更新、削除、監査ログ、移行も枠を使う |

例として50人×26日×6コマの月生成は最大7,800予約。ただし実際の書込行数は索引・監査・再生成時の削除を含めて増える。実人数と実データでrows_read / rows_writtenを確認する。日次枠は開発・検証DBも同一アカウントで合算される点を考慮する。

恒久的な料金や障害ゼロは保証できない。無料プランを維持し、上限到達で課金せず止まる構成とし、定常時・月生成時・初回移行時の枠消費を事前検証する。新規独自ドメイン、有料監視、有料バックアップ、R2等は必須にしない。

Vercel Hobbyは非商用個人利用に制限されるため、塾の実運用を完全無料で継続する前提には採用しない。Firebase Hostingは旧リンクからの転送のため残す。Hostingのrewriteだけで任意の外部Workersを透過プロキシできる前提は置かない。

## 2026-10-28の予定一覧の変更

利用者の希望により、生徒・先生の未来の予定一覧は月選択を廃止し、公開済みの月を日付順に14日ずつ表示する。上記の旧コード調査表にある10日・再来月までの制限は新しい一覧には適用しない。非公開月は飛ばし、生徒は当日より未来、先生は当日以降を対象とする。先生の過去・非公開月の編集には従来の月選択を残す。

DBの取得は日付ページAPI `/api/{role}/attendance` で行う。公開済みの日付だけを最大14日分に絞り、期間条件と対象日リストの両方で予約・カレンダー・人数の取得範囲を限定する。初回だけ名簿と科目を取得し、追加表示では再送しない。テンプレートは予定一覧の取得対象に含めない。先生の予約有無はSetで参照し、生徒×コマごとの予約全件検索を廃止した。月単位の既存APIは管理画面と当日確認のために残す。月をまたぐ未保存の変更は保持する。保存は月ごとの更新番号で競合を検出する。複数月にまたがる保存全体は単一トランザクションではなく、成功した月の変更だけ保留から外し、失敗した分は残して再取得する。

## 共通テンプレートと書き込みの見直し（2026-10-28）

月別の templates は移行元原本として保持し、新システムの編集・生成には attendance_templates を使う。主キーは生徒ID・曜日・コマで、月を含めない。template_state の1行に専用更新番号を持たせる。保存だけなら月の出席予定は変えない。生成時だけ、テンプレートの更新番号と対象月の更新番号を同じDBバッチで検証し、テンプレート更新・対象予約の置換・監査を一括コミットする。個別編集も同じマスターの対象生徒だけを置換する。

先生の出席変更・休講日・科目と、生徒の取消を json_each による集合処理へ変更。予約生成の削除は substr(date) 条件を使わず、日付範囲条件で索引を使う。休講日・科目・公開設定は専用の取得範囲で必要な項目だけ返し、月データが存在しない場合の作成は書き込みバッチ内で行う。生徒の当日表示は1日分と週間件数のみ取得する。

保存後は成功応答の更新番号や確定レコードで画面と画面内キャッシュを更新する。成功前に完了扱いにはしない。途中失敗や競合は未保存の変更を残して再取得する。出席編集、休講日、科目、公開状態、名簿、お知らせ、共通テンプレートの保存後の全量再取得を省いた。ホーム本文は従来から小さい単一バッチと確定応答で処理しており、それを維持する。
